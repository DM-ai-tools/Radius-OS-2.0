Traffic Radius — SEO Agentic Architecture

API + Fallback Edition — one client request in, one verified change live on the website

Marketing pillar · SearchFit skill layer · Direct API orchestration · v1.5 — adds Startup / Mid-Size / Enterprise org-chart skill mapping

01

The request arrives

A request enters through the command center, a chat interface, or a scheduled cadence trigger — carrying who is asking (their role: Strategist, Specialist, Technical, Content, or QA) as well as which client it's about.

Command center / chat / scheduler
02

Role & permission check

Before anything else, the system looks up the requester's role and loads that role's permitted SearchFit skill set and client-tier access. No role can trigger a skill outside its own lane — see the role-based skill assignment below.

Orchestration APIRole permission table
03

The orchestration API receives it

A Python/FastAPI-style backend authenticates the caller, checks rate limits, and validates the request before anything reaches a model. It calls Claude and every other provider directly; nothing is delegated to an external workflow canvas.

Orchestration API (direct calls)
04

The client's profile is pulled

Brand voice, budget, KPIs, automation level, and readiness score are loaded from the Client Digital Profile, so every downstream step already knows this client's rules.

PostgreSQL / Airtable
05

The right SearchFit skill is picked

A fast, cheap model reads the request and the page type (pillar / sub-service / supporting content) to choose one pipeline — but only from the skill set the requester's role is permitted to trigger.

Claude Haiku 4.5
06

A plan is built

The main reasoning model works out what research is needed and in what order. This is the step that makes the system agentic — it decides its own route through the pipeline rather than following one fixed script.

Claude Sonnet 5 — main reasoning
07

Facts are gathered — with a built-in fallback

The plan runs: keyword and site data from GSC/Ahrefs, a site crawl, and competitor research. If a data provider's API is unreachable, the orchestration API itself retries with backoff, then calls a secondary provider directly — no separate automation tool is needed to handle this.

Primary provider + automatic fallback provider

Playbook grounding

TR's own SEO playbooks and cadence rules are fed in, so output follows house standards, not generic advice.

Playbook store

Reuse, don't repay

Competitor research is cached for a set window so the same rivals aren't re-analysed on every run.

Cached results
08

The SEO skill executes

The chosen skill runs with all gathered research, data, and playbook context supplied to it — one of the 15 SearchFit skills, each a reusable, versioned set of instructions.

Claude Sonnet 5
09

A unified report is synthesized

Step outputs are combined into one purpose-driven report — text only at this stage, which keeps every job fast and cheap until a client actually wants to act on it.

Claude Sonnet 5
only if the client wants to act on it
10

The report becomes structured changes

Recommendations are parsed into individually reviewable change items — page URL, change type, priority, confidence, current vs. proposed state — and logged to the suggestion ledger.

Claude Sonnet 5Orchestration API

Confidence decides the shelf, not the gate

  • High confidence → staged for review, not published
  • Medium / low confidence → held pending, flagged for closer review

Nothing auto-applies

Every item is saved as "pending" and waits for a person, regardless of confidence score.

Suggestion ledger
11

Domain review, then QA triage

The specialist who owns that domain reviews it first — Technical reviews technical changes, Content reviews content, never the person who drafted it. SEO Reporting & QA then triages the approval queue. Anything high-risk escalates to a lead regardless of who reviewed it.

Domain reviewerQA approval queue
✓ Approve → build preview✕ Reject → back to step 06
12

A preview is built

Only after approval does the system spend on a dry-run preview — the exact payload that would be sent, with no live CMS writes — so the team sees precisely what will change before it goes anywhere.

Claude, cost-gated
team confirms "publish"
13

Publish — direct API call, with fallback

The orchestration API calls the CMS's own API directly — WordPress, Webflow, or Wix — to push the approved change. Final publish authority sits only with the two lead roles (Senior SEO Strategist for Tier A, Content & On-Page Lead for content changes) — reviewers and specialists can approve into the queue, but cannot trigger this step themselves. If the call fails, the API layer retries with backoff before escalating to a human.

Direct CMS API + built-in retry/backoffLead-restricted
14

Verify — never a silent republish

The system fires an IndexNow submission, then recrawls the URL to confirm the change is actually visible. If it isn't, this raises an in-app notification for a human to review — it never retries silently.

Recrawl + IndexNow
15

Result and audit trail

A verified live page, a set of applied fixes, or a downloadable report — with the full record of what was recommended, approved, and published kept against the client.

Live pageAudit trail

Things that apply throughout

Not steps — these run across the whole system

Not locked to one model

Claude is primary. Specific narrow tasks can fall back to another provider through the same orchestration layer — switching is a config change, not a rebuild.

Built-in resilience

Retries, backoff, and fallback routing (steps 07 and 13) are built directly into the orchestration API — full control over the logic, at the cost of TR's own engineering team owning every connector and retry path.

Role-based access control

Every SearchFit skill has exactly one accountable role (a few deliberately shared). Step 02 enforces this before a skill is ever selected — see the role assignment section below.

Cost is managed by design

Cheap model for skill selection, expensive model only for real reasoning. Competitor research is cached. Reports stay text-only until a client asks to act.

A person is always in the loop

Two mandatory checkpoints — approve the changes, confirm the publish. Nothing reaches a client's live site without a human decision, at any automation level.

Multi-client governance

The client's automation level and readiness score (Client Digital Profile) govern how much of steps 05–12 can ever run without a human — this is per-client, not one blanket rule.

Security

All provider keys and CMS credentials live server-side only. Publish calls are signed so only TR's own orchestration API can trigger them.

Everything is traceable

Every job, report, approval, and publish is logged against the client and request that started it — a complete record of what happened, when, and who signed off.
