Phase 0 · runs once, before Step 01

Business & Project Discovery

Not a SearchFit skill and not a static form — a short workflow that populates the Client Digital Profile before a client's first request ever reaches the pipeline below.

D1

Automated pre-research

Before anyone asks the client a single question, Claude researches their public footprint — website, Google Business Profile, social presence, reviews, visible competitors — and drafts a first pass at products, business model, and positioning.

Claude + web research
D2

Targeted questionnaire, pre-filled

The client only answers what only they know — revenue split, average order value, sales cycle, seasonality, real objectives (checkboxes, not free text), legal/compliance constraints, and marketing spend elsewhere. Pre-filled with D1's findings so the client is confirming, not starting from zero.

Short client questionnaire
D3

Completeness scoring

The assembled profile runs through the same weighted-readiness model used for automation eligibility (Section 7) — applied here to flag exactly which discovery fields are still missing or low-confidence, rather than a form silently sitting half-blank.

Weighted readiness score
D4

Human sign-off

The Client Success Manager reviews before the profile is finalized. Discrepancies between what the client says and what independent research found are surfaced as insight — a client claiming "premium" while public reviews suggest price-sensitive buyers is exactly what discovery should catch, not paper over.

Client Success Manager
D5

Publishes to the Client Digital Profile

The output doesn't live in its own spreadsheet — it populates the Commercial Scope and Marketing Context sections of the Client Digital Profile (Section 6). Every SearchFit skill and pillar agent downstream reads from here, not from a file nobody revisits after onboarding.

Client Digital Profile

Feeds directly into Step 01 below — by the time a request arrives, the profile it needs already exists.

Phase 0.5 · runs once, alongside Phase 0, before Step 01

Access, Tracking & Data Collection

Different character from Phase 0 on purpose: this is mostly API-verifiable, not business context — so most of it is automated, with only the institutional-history step needing a person.

T1

Access collection & connection verification Automated

Credentials requested for CMS, hosting, GSC, GA4, GTM, Google Business Profile, CRM, and call-tracking. Each connection is API-tested, not just assumed granted — "access requested" and "access confirmed working" are treated as different states.

Connection test per platform
T2

Automated tracking audit Automated

Once access exists, tag presence, duplicate tags, cross-domain tracking, referral exclusions, and cookie-consent configuration are scanned directly — the same category of check as a technical SEO crawl, just aimed at the analytics layer instead of the page layer.

GTM / GA4 tag inspection
T3

Conversion tracking validation Automated

Primary and secondary conversions are test-fired to confirm they actually record — forms, calls, email clicks, bookings. A conversion that's configured but not verified firing is treated as not working.

Test-fire + confirm in GA4
T4

Historical baseline & peak/trough analysis Automated

6–12 months (or 3–5 years where available) pulled directly via the GSC and GA4 APIs — pulled automatically, not entered by the client. Beyond the standard baseline, this specifically captures the highest spike and the lowest point in the history: a spike usually means offline activity (radio, TV, print), a collapse usually means a penalty. Running the standard 17-phase process on a penalised site makes it worse, so this has to be known before anything else starts.

GSC API + GA4 APIPeak / trough detection
T5

Known-changes log Human input

The one step no API can do: redesigns, domain moves, past tracking changes, previous SEO campaigns, manual actions, security incidents, and algorithm-update timing live in institutional memory, not in a data source. The account team records this directly with the client.

Client Success Manager + client
T6

Readiness scoring & sign-off Human gate

Run through the same weighted-readiness model as Phase 0. A tracking blocker found here — e.g. conversions configured but not actually firing — holds the client at automation Level 0 regardless of how complete Phase 0 was. Technical SEO Specialist signs off before anything proceeds.

Technical SEO Specialist

Publishes into the Client Digital Profile's System Access and Historical Baseline records — feeds Step 01 alongside Phase 0, and blocks automation eligibility independently of it if tracking isn't verified working.

Publish — direct API call, with fallback

The orchestration API calls the CMS's own API directly — WordPress, Webflow, or Wix — to push the approved change. Final publish authority sits only with the two lead roles (Senior SEO Strategist for Tier A, Content & On-Page Lead for content changes) — reviewers and specialists can approve into the queue, but cannot trigger this step themselves. If the call fails, the API layer retries with backoff before escalating to a human.

Verify — never a silent republish

The system fires an IndexNow submission, then recrawls the URL to confirm the change is actually visible. If it isn't, this raises an in-app notification for a human to review — it never retries silently.

Result and audit trail

A verified live page, a set of applied fixes, or a downloadable report — with the full record of what was recommended, approved, and published kept against the client.

Things that apply throughout

Not steps — these run across the whole system

Not locked to one model

Claude is primary. Specific narrow tasks can fall back to another provider through the same orchestration layer — switching is a config change, not a rebuild.

Built-in resilience

Retries, backoff, and fallback routing (steps 07 and 13) are built directly into the orchestration API — full control over the logic, at the cost of TR's own engineering team owning every connector and retry path.

Role-based access control

Every SearchFit skill has exactly one accountable role (a few deliberately shared). Step 02 enforces this before a skill is ever selected — see the role assignment section below.

Cost is managed by design

Cheap model for skill selection, expensive model only for real reasoning. Competitor research is cached. Reports stay text-only until a client asks to act.

A person is always in the loop

Two mandatory checkpoints — approve the changes, confirm the publish. Nothing reaches a client's live site without a human decision, at any automation level.

Multi-client governance

The client's automation level and readiness score (Client Digital Profile) govern how much of steps 05–12 can ever run without a human — this is per-client, not one blanket rule.

Security

All provider keys and CMS credentials live server-side only. Publish calls are signed so only TR's own orchestration API can trigger them.

Everything is traceable

Every job, report, approval, and publish is logged against the client and request that started it — a complete record of what happened, when, and who signed off.

Foundational Layers vs. Sequential Phases

The 17 phases are not all the same kind of thing. Three of them are foundations that everything else stands on, and one is a continuous layer that runs over the top — only the middle band is genuinely sequential.

↑ Continuous layer — runs over everything

Measurement & Analytics (Phases 16–17)

Reporting, QA, and continuous improvement aren't a final step — they run across every phase below and feed back into them.

Sequential execution band

Phases 3, 5–12

Website audit and sitemap together → competitors → keywords (find, classify, cluster) → URL mapping (optimize an existing page or create a new one) → titles and content calendar for new pages → technical SEO → existing-content audit → lock the selected page → draft that topic with its keyword cluster and show the preview → on-page package and internal linking plan → publish through the connected WordPress account. Phase numbers stay 3, then 5–12. Inside Phase 6, URL mapping runs before the calendar. Phases 13–15 stay out of this band.

↓ Foundational layers — established before, referenced throughout

Competitor Research (Phase 4)

Not a one-time phase. Every role re-runs it against their own task — Content compares content, Technical benchmarks site health, Strategy compares positioning.

Access, Tracking & Data Collection (Phase 2)

Conversion tracking and the historical baseline — including peak/trough detection — must exist before any recommendation can be measured.

Client Baseline & Discovery (Phase 1)

The Client Digital Profile. Everything above reads from it; nothing proceeds without it.

Competitor Research — Depth & Control

Two changes to how competitor analysis works: the operator can override which competitors are used, and the comparison goes down to service level rather than stopping at a single overall score.

Operator override at two points

The system currently auto-selects competitors by industry. That stays as the default, with two override points:

  • At discovery. If the Client Digital Profile lists competitors, those are used. Left empty, the system picks fresh.
  • At review. The auto-selected set can be edited before the analysis runs — remove a poor match, add a specific competitor by name.

Competitor selection is a judgment call the operator is better placed to make than an industry-match heuristic.

Service-level comparison, not one composite score

A single overall similarity score hides the thing that actually matters: different competitors are strong at different services.

  • Comparison runs per service category — SEO, Google Ads, Meta, email marketing, CRO — not just site-wide.
  • The operator selects which services to target and in what order (e.g. Phase 1: SEO + Google Ads + Meta; Phase 2: email + CRO + tracking).
  • For each selected service, the system identifies which competitor is genuinely strongest and benchmarks against that one — an apples-to-apples comparison at category level.
  • Competitor pages are clustered by theme before analysis, so a 6,000-page competitor doesn't blow the budget or bury the finding.

Content Mapping by Funnel Stage

Content planning has to be explicit about which funnel stage each asset serves — otherwise everything defaults to blog posts.

Top of funnel

Awareness

Blog articles, guides, glossary and educational content. High volume, informational intent, low commercial value per page.

Middle of funnel

Consideration

Comparison pages ("X vs Y"), alternatives pages, decision-support and navigational content. This is the layer most often missing entirely.

Bottom of funnel

Decision

Service pages, product pages, case studies, pricing and proof content. Lowest volume, highest commercial value.

Every topic the system generates carries a funnel-stage tag, and the content plan is reviewed for balance across all three — not just how many pieces were produced.

Execution Modes, Dependencies & Guardrails

Human review at every step is the right default while the system is being proven — but it isn't the only mode, and it shouldn't be the only safety mechanism.

Task dependencies decide what can run in parallel

Interdependent — must be sequential

The output of one is the input of the next; there is no way to run these out of order.

  • Keyword research → content brief → content draft
  • Content draft → on-page optimization → publish
  • Site crawl → page-action decisions

Independent — can run in parallel

No prerequisite relationship; blocking these behind other work just adds delay.

  • Technical audit on an existing site
  • Competitor research
  • Tracking and analytics validation
  • Backlink / authority review

Two execution modes

Mode A — Checkpoint (default)

A human reviews at every stage. This is the correct default while outputs are still being validated, and remains mandatory for any client below the readiness and maturity thresholds.

Mode B — Express (pre-approved)

Once a workflow has been proven on a client, it runs start-to-finish through to publish without stopping at each gate. Enabled per client and per workflow — never globally — and only for workflows with a track record. Guardrails below become the safety mechanism in place of the per-step gate.

Guardrail agent — automated checks that replace step-by-step review

An automated reviewer that runs defined checks at each stage. Any failed check stops the workflow by default rather than proceeding on the assumption that output is good.

GuardrailWhat it checks, and why
Trademark keyword blockCompetitor brand terms must never enter client content, regardless of how well they score as keywords. The skill won't know this on its own.
Keyword mix ratioEnforces a defined balance of short / medium / long-tail across an approved keyword set, rather than whatever the model happens to return.
Mobile responsiveness after CROA CRO change validated on desktop can silently break the mobile experience — checked after the change, not before.
Platform capability checkAn outdated CMS version may make a recommended change impossible to implement. Flagged as an external blocker rather than failing silently mid-publish.
Periodic site healthBroken-link and contact-form checks run on a schedule — client-side edits (a promotion, a content update) break things outside any workflow TR ran.

Post-publish self-iterating loop

Publishing isn't the end state. After a change goes live, the system tracks ranking movement, re-checks competitor positions, and monitors live performance — feeding the result back into the next cycle's strategy. This closes the loop from Step 15 back into the foundational layers, and is owned by the SEO QA / Reporting Lead under Continuous SEO Improvement.

Decision framework · applies whenever SearchFit has no skill for a gap

Third-Party Skill Integration Framework

A repeatable process for gaps like Local SEO or Digital PR — not a one-off judgment call each time a useful tool turns up on GitHub or a marketplace.

Step 1 — What format is it actually in?

Low effort

MCP Server

Already speaks the language TR's architecture already uses — Adspirer and SearchFit both connect this way. This is the path of least resistance.

e.g. a Local SEO tool exposed as an MCP endpoint
Medium effort

API-Callable Tool

Needs a thin adapter in the orchestration layer so it can be called as a step — same pattern already used for GSC and Ahrefs.

e.g. a Local SEO SaaS with a documented REST API
High effort

Skill File (Claude Code SKILL.md)

Assumes a terminal, a filesystem, and Claude Code's own skill-loading mechanism. Must be rebuilt as a stateless callable tool before it fits a production API layer.

e.g. a CLI-based audit skill with local dependencies

Step 2 — Mandatory governance, regardless of source

✅ Governance checklist

  1. Role owner assigned. Every skill has exactly one accountable role in the permission table — a new skill can't float outside it.
  2. Domain review → QA gate → lead-only publish. No exception for "the AI used an external tool this time" — the same two-tier review/publish model applies.
  3. Mapped to a cadence phase and page type. Framework first, playbook imposed — a bolted-on tool that doesn't map to the playbook breaks that consistency.
  4. Confidence-scoring defined. Its outputs need to be triageable the same way SearchFit's high/medium/low confidence changes already are.

⚠️ External-sourcing risk checklist

  1. Vendor accountability. If the tool breaks or gets abandoned, that's TR's problem to absorb — there's no SLA to invoke.
  2. Security review. Third-party code wasn't built with TR's multi-tenant isolation in mind — check it before any client data touches it.
  3. Licensing. A five-minute check that's easy to skip and shouldn't be, before depending on it commercially.
  4. Infrastructure footprint. Extra runtime dependencies (e.g. headless browser binaries) are a real cost add, not a free plug-in.

Step 3 — The six-step path from "found on GitHub" to "in production"

1

Confirm the execution model

MCP, API, or skill-file — this decides the integration effort before anything else happens.

2

Build the adapter, if needed

Skill-file and CLI-based tools get wrapped as a stateless callable step — never loaded directly into the production pipeline.

3

Security and license review

Before any client data reaches it — not after it's already live.

4

Assign a role owner

Slotted into the existing role-permission table — most naturally the specialist role closest to that domain.

5

Route through standard governance

Domain review → QA gate → lead-only publish, unchanged from every other skill.

6

Add to a service pack

The skill becomes a line item in the relevant Reusable Client Service Pack — not a standalone bolt-on nobody remembers exists.

"Available on a marketplace" answers the capability question. It never answers the integration question — that work is identical regardless of source. The only thing a third-party origin adds is the maintenance, security, and licensing risk that a SearchFit-built skill doesn't carry.
